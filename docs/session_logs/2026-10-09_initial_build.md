## 4. Что написал сам (ядро)

- `kb/model.py` — модель базы (Bundle, типизированные условия eq/in/cmp/period/known_true/sponsor_basis/and/or/not, показатели с периодами, факты, вопросы, требования).
- `engine/facts.py` — профиль: CONFIRMED / RECOGNIZED / UNKNOWN / CONFLICT, участники, инвалидация зависимых фактов.
- `engine/evaluate.py` — трёхзначная логика, 5 статусов, трасса причин, показатели на дату.
- `engine/planner.py` — выбор следующего вопроса (конфликты → подтверждения → базовые → по весу недостающих фактов).
- `kb/validate.py` — проверки публикации (ссылки, типы, циклы, пересечение периодов, «опубликованное требует подтверждения»).
- `kb/releases.py` — черновик, атомарная публикация, будущие даты, отмена, откат, «требует проверки», кэш снимков.
- `db/migrations/001_init.sql`, `db/conn.py` — схема, WAL, `BEGIN IMMEDIATE`, раннер миграций.
- `ai/interpret.py` — атомарные typed-вопросы JEV из `detect` фактов, разбор ответов, детерминированный парсер чисел/дат.
- `engine/result.py`, `engine/present.py`, `ai/explain.py` — сборка результата только из базы, HTML-рендер, проверка ответа LLM, шаблон.
- `engine/dialog.py` — конечный автомат диалога (кнопки + свободный текст).
- `seed/catalog.yaml` и образец `seed/grounds/pensioner.yaml`.
- `kb/approve.py` — одобрение всей базы/карточки от имени владельца.

## 7. Найденные ошибки и решения

### Найдено мной на живых прогонах
- **Smoke: супруг «не подходит».** Причина в smoke-скрипте (нажимал первую кнопку → супруг стал гражданином Болгарии). Но выявило 2 реальных пробела: нет понятного текста «гражданину Болгарии/ЕС ВНЖ не нужен» и не предлагалась связь «супруг — гражданин Болгарии/ЕС» → добавлены `MemberView.note` и `_spouse_ties`.
- **Член семьи при переезде вместе навсегда «уточнить».** Чл. 33ф требует у заявителя разрешение ≥ 1 года → добавлено требование `sponsor_one_year` и производный факт `status_in_bg=none`, итог «возможно после…».
- **Шум в блоке семьи** (основания супруга «уточнить» с одним совпадением) → показываются только FIT / POSSIBLE_AFTER.
- **JEV пропуски.** «Муж болгарин» JEV относил к супругу → флаг `detect_author` для связей; буквальные формулировки «дети, которые будут жить в Болгарии» → переписаны; enum с двумя близкими вариантами — «неясно» (спрашивается явно, не пропуск). Две метки разметки (c04, c06) исправлены как ошибочные — отмечено в отчёте.

### Сценарные тесты исполнителя (xfail → исправлено мной)
- «Да, верно» молча принимал распознанные списки → списки подтверждаются своим вопросом.
- Предвыбор не обновлялся после предложенной связи → пересчёт по `sel_for`.
- Противоречие по подтверждённому факту молча отбрасывалось → переспрос.

### Codex-ревью №1 (вся сборка, Codex CLI read-only) — 23 замечания, все закрыты
High: LLM мог написать юридическое утверждение («виза не нужна») и ссылку `residence.info` → словарь юридических основ + запрет отрицаний + любые домены; неизвестное исключение давало FIT → CLARIFY; «Почему?»/«Варианты» показывали устаревший результат → пересчёт; переиспользование `sessions.id` → AUTOINCREMENT + токен удаления.

## 9. Работа с сервером (команды выполнял владелец)

1. Найден старый бот: контейнер `bginfo-bot` (образ `bginfobot-bginfo-bot`); остальные контейнеры — другие боты, не тронуты.
2. Остановка: `docker update --restart=no bginfo-bot`, `docker stop bginfo-bot`; конфиг сохранён `docker inspect > ~/bginfo-bot-old-inspect-*.json`.
3. Проверка Telegram: `getWebhookInfo` → `url:""`, `pending_update_count:0`; `getUpdates` → `ok` без 409 — старый бот остановлен полностью, webhook не было.
4. Новый проект в `/opt/bginfo-bot`: токен перенесён из старого контейнера в `.env` через `sed` без вывода на экран; сборка, `check_env`, `up -d`, `seed-draft`.
5. Ошибка: `check_env` показывал `ADMIN_PASSWORD_HASH` — на сервере был старый код; решение `git pull` + `docker compose build`.
6. `/start` → «Сервис готовится» (ожидаемо до публикации).
7. Откат при необходимости: `docker update --restart=unless-stopped bginfo-bot && docker start bginfo-bot`.
