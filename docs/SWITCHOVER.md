# Переключение @bginfosu_bot со старого приложения на новое

> **Выполняется только после явного разрешения владельца.** До него боевой бот не останавливается, его webhook не меняется, его токен в новом проекте не используется. Все проверки до разрешения идут на отдельном тестовом боте.

> **Никогда не запускайте два приложения с одним токеном.** Два получателя обновлений мешают друг другу (Telegram отвечает ошибкой `409 Conflict`), часть сообщений пользователей будет потеряна или обработана не тем приложением. Новый бот сам webhook не удаляет: если webhook настроен, он пишет об этом в лог (`A webhook is configured for this bot`) и завершается.

Команды для сервера. Токен вводится в терминале и не попадает в историю команд:

```bash
read -rs -p "Токен @bginfosu_bot: " TELEGRAM_BOT_TOKEN; echo
export TELEGRAM_BOT_TOKEN
```

Не вставляйте токен в чат, тикеты и логи. По окончании работы закройте сессию терминала или выполните `unset TELEGRAM_BOT_TOKEN`.

## Шаг 1. Подготовить и проверить новый проект на тестовом боте

Условия готовности (все должны выполняться до разрешения на переключение):

- [ ] Развёртывание по [DEPLOY.md](DEPLOY.md) выполнено на **тестовом** токене, `docker compose ps` показывает оба сервиса, `admin` в состоянии `healthy`.
- [ ] Пройдены сценарии из [TEST_SCENARIOS.md](TEST_SCENARIOS.md) (на демо-базе) в Telegram: `/start`, полный опрос, результат, `/delete`.
- [ ] В рабочей базе (`/data/app.db`) **опубликован настоящий выпуск** базы знаний (не демо): карточки проверены по [KB_GAPS.md](KB_GAPS.md) и [KB_MANUAL_UPDATE.md](KB_MANUAL_UPDATE.md). Иначе production-бот либо откажется стартовать (демо-выпуск), либо ответит «база ещё не готова».
- [ ] В `.env`: `APP_MODE=production`, заданы `OPENROUTER_API_KEY`, `CONSULT_CHAT_ID` (если нужны заявки).
- [ ] Сделан бэкап: `docker compose --profile ops run --rm backup`.
- [ ] Владелец дал разрешение на переключение (дата и время зафиксированы).

## Шаг 2. Сохранить конфигурацию старого приложения (для отката)

Запишите и сохраните вне сервера:

- где и как запущено старое приложение (сервер, каталог, systemd-юнит / контейнер / процесс) и **точные команды его остановки и запуска**;
- способ получения обновлений: long polling или webhook;
- файл с токеном/конфигурацией старого приложения (копия, права `600`);
- состояние webhook в Telegram (read-only запрос, ничего не меняет):

```bash
mkdir -p ~/switchover && chmod 700 ~/switchover
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getWebhookInfo" > ~/switchover/webhookinfo-before.json
chmod 600 ~/switchover/webhookinfo-before.json
cat ~/switchover/webhookinfo-before.json
```

В ответе важны поля `url` (адрес webhook, пусто — webhook не настроен) и `pending_update_count` (сколько обновлений ждёт доставки). Файл может содержать секретную часть адреса webhook: не публикуйте его.

## Шаг 3. Остановить старый процесс получения обновлений

Остановите старое приложение той командой, которую записали в шаге 2 (способ зависит от того, как оно запущено). Проверьте, что процесс действительно остановился и не перезапускается сам (политика `restart`, systemd `Restart=`, cron, supervisor).

С этого момента пользователи не получают ответов; обновления копятся в Telegram (хранятся не дольше 24 часов).

## Шаг 4. Проверить webhook

```bash
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getWebhookInfo"
```

- `"url":""` — webhook не настроен, переходите к шагу 5.
- `"url":"https://..."` — старое приложение работало через webhook. Новому боту (long polling) webhook мешает, и он не запустится. Удалять webhook можно **только в рамках разрешённого переключения**, после шагов 2 и 3 и после выбора из шага 5:

```bash
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/deleteWebhook"
```

Эта команда **сохраняет** накопленные обновления (`drop_pending_updates` не передан, значит false). Поле `pending_update_count` покажет, сколько их. Если нужно сбросить, см. шаг 5.

## Шаг 5. Явно выбрать: сохранить накопленные обновления или сбросить

Решение принимает владелец; молча терять сообщения нельзя. Посмотрите `pending_update_count`:

```bash
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getWebhookInfo"
```

| Вариант | Что произойдёт | Когда выбирать |
|---|---|---|
| **Сохранить** (по умолчанию, ничего не делать) | Новый бот при запуске получит накопленные обновления (до 24 часов). Текстовые сообщения и команды обработаются как обычно. Нажатия **старых кнопок** новый бот не поймёт и ответит «Эта кнопка устарела». Анкеты старого приложения новый бот не знает: пользователь начнёт заново. | Если пользователи писали за время простоя и важно им ответить. |
| **Сбросить** | Все накопленные обновления удаляются безвозвратно. | Если накопилось много устаревших нажатий и сообщений, и отвечать на них не нужно. |

Сброс (необратим):

```bash
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/deleteWebhook?drop_pending_updates=true"
```

Запишите принятое решение и значение `pending_update_count` на момент решения.

## Шаг 6. Запустить новое приложение с production-токеном

На сервере нового приложения:

```bash
cd /opt/bginfo-bot
nano .env
```

Поставьте боевой `TELEGRAM_BOT_TOKEN` и `APP_MODE=production`, затем:

```bash
docker compose up -d
docker compose ps
docker compose logs --tail=50 bot
```

В логе не должно быть `A webhook is configured for this bot` и `Active knowledge release is marked demo`. Если они есть, бот не запущен: вернитесь к шагу 4 или опубликуйте настоящий выпуск базы.

## Шаг 7. Проверить работу

В Telegram со своего аккаунта в боевом `@bginfosu_bot`:

1. `/start`: приходит приветствие.
2. Полный опрос до результата (кнопками и, если включён OpenRouter, свободным текстом), кнопки «Почему этот вариант?» и «Какие ещё варианты?».
3. `/delete` и повторный `/start`.
4. Заявка на консультацию (если настроен `CONSULT_CHAT_ID`): приходит в нужный чат.
5. Админка (SSH-туннель или HTTPS): вход работает, действующий выпуск — настоящий, на главной нет предупреждения о демо; в «Статистике» видны события.
6. `docker compose logs --tail=100 bot` без ошибок.

Если на любом шаге проблема, переходите к шагу 8.

## Шаг 8. Откат при проблеме

1. Остановите новое приложение (бот; админку можно оставить):

   ```bash
   cd /opt/bginfo-bot
   docker compose stop bot
   docker compose ps
   ```

2. Верните старый способ получения обновлений:
   - **Старое приложение работало через long polling**: достаточно запустить его прежней командой из шага 2.
   - **Старое приложение работало через webhook**: сначала запустите приложение, принимающее webhook, затем восстановите webhook на прежний URL из `~/switchover/webhookinfo-before.json`. Адрес берётся из поля `url`:

     ```bash
     OLD_URL=$(python3 -c "import json; print(json.load(open('$HOME/switchover/webhookinfo-before.json'))['result']['url'])")
     curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" --data-urlencode "url=$OLD_URL"
     ```

     Если у старого webhook были дополнительные параметры (`secret_token`, `allowed_updates`, `max_connections`), они не показываются в `getWebhookInfo` целиком (секретный токен не показывается совсем) и берутся из сохранённой конфигурации старого приложения (шаг 2).

3. Проверьте: `curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getWebhookInfo"` и `/start` в боте.
4. Сообщения, накопленные за время простоя, будут доставлены старому приложению, если вы не сбрасывали их в шаге 5.
5. Разберите причину и повторите переключение только после нового разрешения владельца.
