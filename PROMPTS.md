# Запросы к JEV и генеративной модели

Бот обращается к двум разным моделям через OpenRouter. Всё остальное (статусы, условия, суммы, сроки, ссылки, тексты правил) делает код по базе знаний.

| Что | Кто | Эндпоинт | Модель (config.ini) | Файл |
|---|---|---|---|---|
| Разбор свободного текста в факты | JEV | `POST {base_url}/systemone` | `[ai] jev_model` = `~typesafe/jev-latest` | `src/bginfo/ai/interpret.py` |
| Извлечение названных сумм | генеративная модель | `POST {base_url}/chat/completions` (строгая JSON-схема) | `[ai] llm_model` = `openai/gpt-4.1-mini` | `src/bginfo/ai/interpret.py` |
| Персональное объяснение результата | генеративная модель | `POST {base_url}/chat/completions` (строгая JSON-схема) | `[ai] llm_model` | `src/bginfo/ai/explain.py` |

`base_url` = `https://openrouter.ai/api/v1`. Документация: JEV — <https://openrouter.ai/docs/guides/community/jev>, запрос System One — <https://openrouter.ai/docs/api/api-reference/systemone/submit-a-system-one-request>.

Общие правила:

- Любой вызов проходит через учёт лимитов `ai/ledger.py`: суточный бюджет `[limits] daily_budget_usd` и дневные лимиты на пользователя `user_text_per_day` (JEV и извлечение сумм) и `user_explain_per_day` (объяснение). Превышение или сбой AI не ломают анкету: бот продолжает кнопками, а объяснение заменяется шаблоном.
- Без `OPENROUTER_API_KEY` оба вида вызовов отключены.
- В лог и в таблицу `ai_calls` не пишутся ни тексты пользователей, ни ключи: только тип вызова, модель, статус, токены, стоимость (`usage.cost`), задержка.

## 1. JEV (разбор текста)

### Когда вызывается

Когда человек пишет текст, а не нажимает кнопку. Если сейчас задан вопрос и короткий ответ разбирается простым правилом без AI (`parse_simple`: «да», «нет», «не знаю», название варианта, число, сумма, дата), JEV не вызывается. Сообщение длиннее 1500 символов (`MAX_TEXT` в `engine/dialog.py`) отклоняется до вызова; в JEV уходит не больше 4000 символов. Если JEV недоступен (нет ключа, сбой, лимит), бот пишет «Сейчас не получается разобрать текст… продолжим кнопками».

### Что отправляется

```json
{
  "model": "~typesafe/jev-latest",
  "state": {"user_message": "<текст человека>"},
  "questions": { "<id>": {"type": "choice", "instructions": "...", "criteria": {"<вариант>": "<описание>"}} }
}
```

Все вопросы имеют тип `choice` (по документации JEV типы: `noul`, `choice`, `score`; для ответов «да / явно нет / не указано / противоречие» нужен `choice`). Ответ: для каждого вопроса `choice` (выбранный вариант) и `probabilities` (вероятности по вариантам); в `usage.cost` приходит стоимость.

### Какие вопросы строятся

Вопросы собирает `build_questions` из действующего выпуска базы знаний, поэтому новый факт с заполненным полем «вопрос для JEV» (`detect`) начинает распознаваться без правки кода.

1. **`intent`**: «Что делает автор этим сообщением?» Варианты (`criteria`):

   | Вариант | Описание |
   |---|---|
   | `answer_current` | Сообщение отвечает на текущий вопрос бота (в описание подставляется текст текущего вопроса; вариант есть, только если сейчас есть вопрос) |
   | `new_info` | Человек рассказывает о своей ситуации: кто переезжает, гражданство, доходы, работа, семья, жильё |
   | `correction` | Человек исправляет то, что сообщал раньше («нет, не так», «я ошибся», «на самом деле») |
   | `question_to_bot` | Человек задаёт вопрос боту или просит что-то пояснить |
   | `wants_buttons` | Человек передумал писать сам и просит, чтобы бот задавал вопросы |
   | `other` | Сообщение не относится к переезду и проживанию в Болгарии |

   Что делается с ответом: `wants_buttons` (уверенность не ниже 0.5) переводит анкету на кнопки; `other` (не ниже 0.6, без распознанных сведений) даёт ответ «Я помогаю только с подбором…» и продолжение анкеты; `question_to_bot` (не ниже 0.6, без сведений) показывает подсказку текущего вопроса; в остальных случаях сообщение разбирается как новые сведения или исправление. Суммы из текста ищутся, только если намерение `new_info`, `correction` или `answer_current` и в тексте есть цифра.

2. **Вопросы `f1`, `f2`, … по `detect` у фактов и вариантов.** Для каждого да/нет-факта с `detect` и для каждого варианта enum/multi-факта с `detect` строится отдельный вопрос с `instructions` = текст `detect` (атомарный вопрос вида «Указано ли, что …?»).

   - Для фактов участников (гражданство, доходы) `criteria`: `self` (сказано об авторе или «о нас» вместе с автором), `spouse` (о супруге), `other_member` (о другом члене семьи), `explicit_no` (прямо сказано, что этого нет), `not_mentioned`, `contradiction`.
   - Для фактов анкеты и фактов с признаком «ситуация автора» (`detect_author`) `criteria`: `yes`, `explicit_no`, `not_mentioned`, `contradiction`.

   Что делается с ответом (`map_answers`, чистая функция, тестируется без сети):

   - Вариант `self`/`spouse`/`other_member`/`yes` с вероятностью не ниже `[ai] jev_recognize_threshold` (0.3) записывается как **распознанное** сведение (не подтверждённое). Человек подтверждает его кнопкой «Да, верно».
   - `explicit_no` с вероятностью не ниже `[ai] jev_negation_threshold` (0.75) для да/нет-факта записывается как распознанное «нет», тоже с подтверждением.
   - `contradiction` с вероятностью не ниже 0.4 помечает факт «неясно»: бот спросит его явно кнопками.
   - Если два варианта одного enum-факта правдоподобны (оба не ниже порога, разница вероятностей меньше 0.3), факт тоже помечается «неясно».
   - `not_mentioned` ничего не исключает: основания, о которых текст молчит, остаются открытыми и проверяются контрольными вопросами анкеты.
   - JEV сам ничего не исключает и не принимает решений: вывод о статусе делает код после подтверждения человеком.

3. **`current`**: «Какой ответ на вопрос «<текст вопроса>» содержится в сообщении?» Есть, когда текущий вопрос — enum или да/нет. `criteria` — варианты ответа вопроса (для да/нет: `yes` «Да», `no` «Нет») плюс `unclear` («Из сообщения ответ на этот вопрос не ясен»). Ответ принимается, если выбран не `unclear` и вероятность выбранного варианта не ниже 0.6 (константа в `map_answers`).

Результаты оценки на размеченных примерах (пропуски, ложные срабатывания, стоимость) — [docs/JEV_EVAL.md](docs/JEV_EVAL.md). Набор примеров — `tests/jev_eval/cases.yaml`.

## 2. Генеративная модель: извлечение сумм

### Когда вызывается

После JEV, если в тексте есть хотя бы одна цифра, намерение `new_info` / `correction` / `answer_current` и в базе есть денежные факты участников (`money`, `scope: person`: например, пенсия, доход, сумма инвестиции). Нужен, потому что JEV отвечает на вопросы «указано ли», а числа не извлекает.

### Что отправляется

`messages`: системная инструкция и текст человека (не более 2000 символов). Параметры: `max_tokens` 300, `temperature` 0, `response_format` = строгая JSON-схема `amounts`.

Системная инструкция собирается на лету (в неё подставляется список денежных фактов выпуска в виде «ключ — подпись»):

```
Извлеки из сообщения пользователя только явно названные суммы денег. Не додумывай. Для каждой суммы выбери поле fact строго из списка: <ключ — подпись; ключ — подпись; ...>. Если сумма не подходит ни к одному полю, не включай её. who: self — автор, spouse — супруг(а).
```

Схема `AMOUNT_SCHEMA`:

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["amounts"],
  "properties": {
    "amounts": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["fact", "who", "value", "currency"],
        "properties": {
          "fact": {"type": "string"},
          "who": {"type": "string", "enum": ["self", "spouse"]},
          "value": {"type": "number"},
          "currency": {"type": "string", "enum": ["EUR", "BGN", "OTHER"]}
        }
      }
    }
  }
}
```

### Что проверяется программно

Каждая найденная сумма отбрасывается, если: `fact` не из списка денежных фактов; `who` не `self`/`spouse`; значение не в диапазоне больше 0 и меньше 10 000 000; валюта `OTHER`; целая часть суммы не встречается в цифрах исходного текста (защита от выдумки). Левы пересчитываются в евро по фиксированному курсу 1,95583. Принятая сумма записывается как **распознанная** (не подтверждённая), человек подтверждает её вместе с остальным.

## 3. Генеративная модель: итоговое объяснение

### Когда вызывается

После того как код посчитал результат (`kind` равен `ok` или `individual`, есть хотя бы одно основание для показа). Всегда сначала строится проверенный шаблонный вариант («Вы указали: …»); модель только заменяет его, если ответ прошёл проверку.

### Что отправляется

`messages`: системный промпт и JSON-нагрузка (`build_payload`). Параметры: `max_tokens` = `[ai] explain_max_tokens` (900), `temperature` 0.2, `response_format` = строгая схема `explanation`.

Нагрузка (`json.dumps`, `ensure_ascii=False`): `profile` (список «подпись: значение» подтверждённых ответов), `grounds` (для главного основания и до трёх альтернатив: `id`, `title`, `status` (формулировка статуса), `met`, `unknown`, `unmet` (подписи условий), `facts` (ответы, использованные в расчёте)), `family` (для каждого члена семьи подпись и список «название основания, статус»).

### SYSTEM_PROMPT (дословно из `ai/explain.py`)

```
Ты помогаешь объяснить человеку результат предварительного подбора оснований для проживания в Болгарии.
Решение уже принято программой по проверенным правилам. Твоя задача — только персонально пересказать его простыми словами.

Правила:
- Пиши по-русски, просто, на «вы», без канцелярита.
- intro: 1–2 предложения о том, что получилось, без перечисления всех вариантов.
- grounds: для КАЖДОГО переданного основания (id без изменений) одно-два предложения «почему», опираясь только на ответы человека (facts) и выполненные/невыясненные условия (met/unknown).
- family: 1–2 предложения о членах семьи, если они есть во входных данных; иначе пустая строка.
- Не меняй статусы и не спорь с ними. Не добавляй других оснований.
- Не пиши никаких сумм, процентов, сроков, дат и чисел, кроме тех, что есть во входных данных.
- Не добавляй требований, документов, сроков и ссылок, которых нет во входных данных.
- Не обещай результат: никаких «гарантированно», «точно дадут», «одобрят».
- Без HTML и markdown.
```

### Схема ответа `SCHEMA`

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["intro", "grounds", "family"],
  "properties": {
    "intro": {"type": "string"},
    "grounds": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["id", "why"],
        "properties": {"id": {"type": "string"}, "why": {"type": "string"}}
      }
    },
    "family": {"type": "string"}
  }
}
```

### Программная проверка `check` и откат на шаблон

Валидный по схеме JSON ещё не значит правильный. `check(data, payload, all_titles)` возвращает список проблем; если он не пуст, **вся** персонализация отбрасывается и показывается шаблон («Вы указали: …»; вступление и текст о семье пустые). Проверяется:

- набор `id` в ответе совпадает с переданным (нельзя добавить или потерять основание);
- каждый текст (`intro`, `family`, каждое `why`) не длиннее 450 символов;
- в тексте нет ссылок (`http(s)://`, `www.`, домены `.eu/.bg/.com/.org/.net/.ru`, `t.me/`);
- нет `<` и `>` (разметки);
- нет обещаний результата (стоп-фразы: «гарант…», «точно да/получ/одобр…», «одобрят», «100 %», «без проблем», «наверняка», «стопроцентн…»);
- все числа в тексте присутствуют во входной нагрузке (нельзя придумать сумму, срок, процент);
- не упомянуто основание, которого нет среди показанных (по названиям из всей базы);
- текст о семье допустим только если члены семьи были во входных данных;
- ни одно пояснение `why` не пустое.

Результат проверки записывается в `ai_calls` (поля `ok` и `error`), отклонение пишется в лог без текста. При ошибке сети, лимите или бюджете тоже используется шаблон. Итоговый источник (`llm` или `template`) сохраняется вместе с результатом.

## 4. Что модели НЕ передаётся

- Идентификаторы Telegram: id, username, имя, id чата.
- Паспортные данные, телефоны, адреса и любые контакты: бот их не запрашивает и не сохраняет, а в уведомлении об AI просит их не присылать.
- В объяснение (раздел 3) **не уходит исходный текст человека**: только структурированные ответы анкеты (подписи и значения), названия оснований, статусы, подписи выполненных и невыясненных условий. Свободный текст получают только JEV (до 4000 символов) и, при наличии цифр, извлечение сумм (до 2000 символов).
- Тексты правил, ссылки, суммы и сроки из базы в запрос не передаются как «знание»: статусы и условия модель не вычисляет, а только пересказывает уже посчитанное. Числа в ответе обязаны совпасть со входом.
- Ключ OpenRouter и данные других пользователей.

См. также [docs/PRIVACY.md](docs/PRIVACY.md).

## 5. Как менять модель

Модели и параметры лежат в `config.ini`, секция `[ai]`:

```ini
jev_model = ~typesafe/jev-latest
llm_model = openai/gpt-4.1-mini
explain_max_tokens = 900
jev_recognize_threshold = 0.3
jev_negation_threshold = 0.75
timeout_s = 20
retries = 2
```

1. Измените значение (идентификатор модели на <https://openrouter.ai/models>). Для `llm_model` модель должна поддерживать структурированный вывод по JSON-схеме (`response_format: json_schema`), иначе вызовы будут завершаться ошибкой, а бот перейдёт на шаблоны.
2. Локально перезапустите бота. В Docker `config.ini` копируется в образ: `docker compose build && docker compose up -d`.
3. Проверьте живыми прогонами (платные): после смены `llm_model` — `python scripts/smoke_live.py -v` (в конце виден источник объяснения `llm` или `template`); после смены `jev_model` или порогов — `python scripts/jev_eval.py` и сравните `docs/JEV_EVAL.md` (главная метрика — «пропущено направлений»).
4. Правка текста самих промптов — это правка кода (`INTENTS`, `PERSON_LABELS`, `CASE_LABELS`, `AMOUNT_SCHEMA` и системная инструкция в `ai/interpret.py`; `SYSTEM_PROMPT`, `SCHEMA`, правила `check` в `ai/explain.py`) и требует тестов. Тексты вопросов для JEV по фактам (`detect`) правятся в админке без кода.
